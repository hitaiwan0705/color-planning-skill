# W03｜色彩表徵與可交換色彩資料、色票三屬性排列

---

## 這一週在解什麼問題

打開你的設計檔，取色器告訴你這個紅是 `#D32F2F`。
現在把這串字傳給印刷廠。

**印出來會是什麼顏色？沒有人知道。**

因為 `#D32F2F` 不是一個顏色，它是**給某台裝置的驅動訊號**。
同一組 RGB 送進不同的螢幕，會發出不同的光譜，於是產生不同的顏色。
這不是誤差，是定義問題——這組數字從來就沒說過自己是什麼顏色。

### 分界線：裝置相關 vs 裝置無關

| 類型 | 例子 | 它描述的是 |
|---|---|---|
| **裝置相關**（device dependent） | 螢幕 RGB、印表機 CMYK | 驅動某台機器的訊號 |
| **裝置無關**（device independent） | CIE XYZ、CIELAB | 人眼會看到什麼 |

**這條分界是整學期的地基。** 之後的 ICC、rendering intent、色域對映，
全部都在回答同一個問題：*這台裝置的訊號，對應到哪個裝置無關的顏色？*

---

## 主線：XYZ → CIELAB／LCh → ΔE → ICC

這條線上每一步都是為了解決前一步解不掉的問題。照順序理解它，
比分開背四個名詞有用得多。

### ① CIE XYZ：先有一套「大家都同意」的數字

XYZ 是把「光源 × 物體反射率 × 人眼色匹配函數」三者相乘積分的結果。
它讓兩個人可以用同一組數字談同一個顏色。

**但 XYZ 相同不代表顏色會相配。** 你必須同時指定三件事：
**量測幾何、照明體、觀察者**。少講其中一個，那組 XYZ 就沒有意義。
W06 的量測條件表就是在記這三件事。

### ② CIELAB／LCh：讓「差多少」變成可算的距離

XYZ 空間裡，數值差得一樣多，人眼感覺到的差異卻差很多。
CIELAB 把它拉得比較均勻，並給出三個對得上人類語言的軸：

```
L*  明度      0（黑）～ 100（白）
a*  紅／綠    正為紅、負為綠
b*  黃／藍    正為黃、負為藍
```

`LCh` 是同一組數字換成圓柱座標：**L\* 明度、C\* 彩度、h 色相角**。
指定顏色時用 LCh 比用 a\*b\* 直覺得多——「彩度降一點、色相不要動」
在 LCh 裡就是改一個數字，在 a\*b\* 裡要改兩個。

**一個常被跳過的重點**：CIELAB 的數值**永遠相對於一個參考白**。
沒有講參考白的 L\*a\*b\*，和沒有講單位的長度一樣。

### ③ ΔE：把「差多少」變成一個數字

兩色在 CIELAB 裡的距離就是色差。但公式有很多版本，
**本課一律用 CIEDE2000（ΔE00），且引用時必須註明版本，不得與 CIE76 混用。**

為什麼要挑版本？因為同一對顏色，不同公式算出來的數字不一樣。
你在報告裡寫「ΔE = 3.2」而不說哪個公式，對方無法判斷這是好是壞。

本課的 ΔE00 一律由 `tools/color/scripts/color_audit.py` 產生，不得手算或估算。

### ④ ICC：讓不同裝置之間可以換算

有了裝置無關的數值，才能替每一台裝置建立「我的訊號 ↔ 那個顏色」的對應表。
那張表就是 ICC profile。W07、W08 專門講它。

## design token：把顏色變成可交接的資料

一個顏色要能交接，光有數值不夠。本課要求的最小欄位：

| 欄位 | 為什麼必要 |
|---|---|
| `id` | 唯一識別。改色時知道改的是哪一個 |
| `color_space` | 沒有色彩空間的數值沒有意義 |
| `value` | 數值本身 |
| `source_file` | 這個數值從哪個檔案取的 |
| `profile` + `version` | 同一組 RGB 配不同 profile 是不同顏色 |
| `role` | 這個色在系統裡做什麼（主色／警示／背景） |

```json
{
  "id": "brand.primary",
  "color_space": "sRGB",
  "value": "#0072B2",
  "source_file": "logo_master.ai",
  "profile": "sRGB IEC61966-2.1",
  "profile_version": "v2",
  "role": "品牌主色"
}
```

**跨色彩空間不得直接比較。** sRGB 的 `#0072B2` 和某個 CMYK 值即使「看起來一樣」，
也不能寫成相等——要比較必須先都轉到裝置無關空間，並記錄轉換來源。

### OKLCH：值得知道，但不是本課主線

OKLCH 是近年在網頁與介面設計上流行的表示法，性質接近 LCh 但在感知均勻性上
做了修正，調整明度時色相偏移較小。**本課允許在 design token 裡並列記錄 OKLCH**，
但判準仍以 CIELAB／LCh 與 ΔE00 為準——因為量測儀器與 ICC 走的是這一條。

### Pantone 的位置

Pantone 是**產業溝通與色票指定**的工具：你和廠商說「PANTONE 186 C」，
對方知道要調哪一罐油墨。它非常有用。

**但它不是色彩科學的起點。** 理由：Pantone 編號本身不告訴你在什麼觀察條件下、
用什麼量測幾何得到什麼數值。編號後面的 `C`／`U`／`M` 指的是塗佈紙、
非塗佈紙、模造紙——**同一個編號印在不同紙上就是不同的顏色**。

所以本課的規則是：Pantone 只能出現在 design token 的「色票指定」欄位，
不得作為色彩科學推導的起點。

## 實體操作：依三屬性排列色票

> 本節對應 iPAS 科目二評鑑細目 **L12101**。
> 科目二是**實作測驗**，紙本試題搭配實體色票貼紙作答。
> 這是動手題，看講義看不會。

### 為什麼要練這個

排列色票逼你把「色相／明度／彩度」三個維度**分開**看。
多數人平常是混著看的——說「這個比較深」時，可能指明度低，也可能指彩度高。
排錯的地方，就是你三個維度還沒分開的地方。

### 操作步驟

**準備**：一組色票（20–30 張）、白色襯紙、D65 或 D50 燈箱（本課燈箱兩種光源皆有）。

1. **先只看色相**：把所有色票依色相環順序排成一圈，不管深淺與鮮豔。
   遇到「這張到底算紅還算橙」時，把它暫時放在兩者之間，不要硬塞。
2. **固定一個色相，排明度**：抽出同色相的一組，由亮到暗排成一列。
   瞇眼看——瞇眼會壓掉彩度資訊，讓明度差變明顯。
3. **固定色相與明度，排彩度**：由灰到鮮排。這一步最難，
   因為高彩度的色票常常看起來也比較亮。
4. **交叉檢查**：任取兩張，說出它們差在哪一個維度。說不出來就是還沒分開。

### 三個常見的卡點

| 卡點 | 徵狀 | 怎麼處理 |
|---|---|---|
| 明度與彩度混淆 | 把鮮豔的黃排得比淺灰更「亮」 | 瞇眼或轉灰階看，只剩明度資訊 |
| 色相邊界不確定 | 紫紅／紅紫排不出順序 | 用相鄰兩張比較，不要跟遠處的比 |
| 光源影響 | 換張桌子排出來的順序不一樣 | 全程在同一個燈箱、同一個背景下做 |

**注意**：這一步就已經在做色彩感知的觀察了。
換光源會改變排序，這件事在 W10 之後會變成正式的觀察資料。

## 本週交付

本週發放 **TASK-02**，W04 收件。交付物如下：

- `design_token_table.json`：每個 token 具備 id、色彩空間、數值、來源檔、profile 名稱與版本
- 色彩表徵對照表：同一色票在指定的兩種以上色彩空間下的數值，並註明轉換來源
- 色票版本紀錄
- `color_audit.py` 的輸出檔（JSON 原檔，不是截圖）
- 色票三屬性排列的照片與排列說明，說明中須指出你在哪一步卡住、如何處理
- AI 使用揭露

## 失敗條件

- token 缺 id 或缺 profile → 未通過
- RGB／CMYK／Lab 數值未標來源檔 → 該筆數值不採計
- 跨色彩空間直接比較而未註記限制 → 未通過
- 以 Pantone 編號作為色彩科學推導的起點 → 該段作廢
- 色差數值未註明 CIEDE2000，或與 CIE76 混用 → 該數值不採計
- 排列說明只寫「排好了」而未指出卡點 → 退回重寫
